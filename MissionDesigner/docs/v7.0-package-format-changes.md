# v7.0 Package Format Changes

**Date:** 2026-04-04
**Applies to:** `.WFmasterX` (runtime packages), `.WFlibX` (workflow library packages), `.WFslibX` (step library packages)

This document describes all changes to the workflow package specification format introduced in v7.0 (Child Workflow & Versioning Redesign). The runtime must be updated to accept these changes.

---

## Summary of Changes

| Change                                                                              | Impact                 | Backward Compatible                                |
| ----------------------------------------------------------------------------------- | ---------------------- | -------------------------------------------------- |
| New `children` array on workflow specs                                              | Must parse             | Yes — old packages still use `child_workflows`     |
| `ChildWorkflowExport` type replaces flat `MasterWorkflowSpecification` for children | Must handle new fields | Yes — superset of old type                         |
| `version` and `state` fields on root and child specs                                | Must read              | Yes — optional on root, always present on children |
| `schemaVersion` now `"4.0"`                                                         | Must accept            | Yes — `"3.0"` packages still valid                 |
| `child_workflows` deprecated but still emitted for backward compat                  | No action needed       | N/A                                                |

---

## 1. New `children` Array

### Before (v6.0)

Child workflows were stored in `child_workflows` as plain `MasterWorkflowSpecification[]`:

```json
{
  "local_id": "My Workflow",
  "oid": "123456",
  "steps": [...],
  "connections": [...],
  "child_workflows": [
    {
      "local_id": "Child Workflow",
      "oid": "789012",
      "steps": [...],
      "connections": [...],
      "child_workflows": []
    }
  ]
}
```

### After (v7.0)

Child workflows are now in `children` as `ChildWorkflowExport[]` with additional metadata:

```json
{
  "local_id": "My Workflow",
  "oid": "123456",
  "version": "1.0.0",
  "state": "Draft",
  "schemaVersion": "4.0",
  "steps": [...],
  "connections": [...],
  "children": [
    {
      "local_id": "Child Workflow",
      "oid": "789012",
      "version": "1.0.0",
      "state": "Draft",
      "parentChildSpecId": null,
      "schemaVersion": "4.0",
      "steps": [...],
      "connections": [...],
      "children": [
        {
          "local_id": "Grandchild Workflow",
          "oid": "345678",
          "version": "1.0.0",
          "state": "Draft",
          "parentChildSpecId": "789012",
          "schemaVersion": "4.0",
          "steps": [...],
          "connections": [...]
        }
      ]
    }
  ]
}
```

### Runtime Handling

1. **Prefer `children` over `child_workflows`** — if both are present, use `children`
2. **Fall back to `child_workflows`** — for packages exported before v7.0
3. The `children` array is a nested tree (recursive), not flat

---

## 2. ChildWorkflowExport Type

Each entry in the `children` array is a `ChildWorkflowExport`, which extends `MasterWorkflowSpecification` with three additional required fields:

| Field               | Type                | Description                                                                                                                                       |
| ------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parentChildSpecId` | `string \| null`    | Links this child to its parent in the tree. `null` = direct child of the root workflow. Non-null = OID of the parent child spec in the same tree. |
| `version`           | `string` (required) | Semver version string, always set (e.g., `"1.0.0"`). Not optional like on root specs.                                                             |
| `state`             | `string` (required) | Lifecycle state, always set (e.g., `"Draft"`). Not optional like on root specs.                                                                   |

### parentChildSpecId Linkage

The `parentChildSpecId` field establishes the tree hierarchy:

```
Root Workflow (not in children array)
  children[0]: { parentChildSpecId: null }        ← direct child of root
    children[0]: { parentChildSpecId: "oid-of-parent-child" }  ← grandchild
  children[1]: { parentChildSpecId: null }        ← another direct child
```

When `parentChildSpecId` is non-null, its value is the `oid` of another entry in the same `children` tree (the parent at the level above).

## 3. Version and State Fields

### On Root Specification (`MasterWorkflowSpecification`)

Two new **optional** fields added:

| Field     | Type      | Default   | Values                                     |
| --------- | --------- | --------- | ------------------------------------------ |
| `version` | `string?` | `"1.0.0"` | Semver string (e.g., `"1.0.0"`, `"2.1.3"`) |
| `state`   | `string?` | `"Draft"` | One of the lifecycle states below          |

These fields are optional on root specs for backward compatibility — older export paths may omit them.

### On Child Specifications (`ChildWorkflowExport`)

The same fields but **required** (always present):

| Field     | Type                | Values                            |
| --------- | ------------------- | --------------------------------- |
| `version` | `string` (required) | Semver string                     |
| `state`   | `string` (required) | One of the lifecycle states below |

### Specification Lifecycle States

```
Draft → InTest → InReview → Approved → Effective → Superseded → Obsolete
```

| State        | Meaning                       |
| ------------ | ----------------------------- |
| `Draft`      | Initial state, being authored |
| `InTest`     | Under testing                 |
| `InReview`   | Under review for approval     |
| `Approved`   | Approved but not yet active   |
| `Effective`  | Active/current version        |
| `Superseded` | Replaced by a newer version   |
| `Obsolete`   | No longer valid               |

### Runtime Handling

- If `version` is missing, treat as `"1.0.0"`
- If `state` is missing, treat as `"Draft"`
- The runtime may use `state` to determine which version to execute (e.g., prefer `Effective` over `Draft`)

---

## 4. Schema Version

The `schemaVersion` field on `MasterWorkflowSpecification` is now `"4.0"`:

```json
{
  "schemaVersion": "4.0",
  "local_id": "My Workflow",
  ...
}
```

### Runtime Handling

- Accept `"4.0"` in addition to `"3.0"`
- The `schemaVersion` field may be absent on older packages — treat as valid
- Reject `"2.0"` and below (format is incompatible)

---

## 5. Deprecated: `child_workflows`

The `child_workflows` field is **deprecated but still present** in v7.0 exports for backward compatibility:

```json
{
  "children": [...],           // NEW: preferred, always present in v7.0 exports
  "child_workflows": [...]     // DEPRECATED: retained for v6.0 runtime compat
}
```

### Runtime Handling

- **If both `children` and `child_workflows` exist:** use `children` (ignore `child_workflows`)
- **If only `child_workflows` exists:** use it (pre-v7.0 package)
- **If only `children` exists:** use it
- **If neither exists:** workflow has no child workflows

### Differences Between the Two Formats

| Aspect             | `child_workflows` (v6.0)            | `children` (v7.0)                                             |
| ------------------ | ----------------------------------- | ------------------------------------------------------------- |
| Type               | `MasterWorkflowSpecification[]`     | `ChildWorkflowExport[]`                                       |
| Extra fields       | None                                | `parentChildSpecId`, `version` (required), `state` (required) |
| Nesting            | `child_workflows` within each child | `children` within each child                                  |
| Grandchild linkage | Implicit (nested position)          | Explicit (`parentChildSpecId` points to parent OID)           |

## 6. ZIP Package Structure (Unchanged)

The ZIP file structure for `.WFmasterX` runtime packages is **unchanged**:

```
MyWorkflow.WFmaster          ← JSON workflow specification (with children/child_workflows)
manifest.json                ← Package metadata
environments/
  EnvLib.WFenvir             ← Environment library JSON
actions/
  ActionLib.WFaction         ← Action library JSON
images/
  imageOid-filename.jpg      ← Form element images (OID-prefixed)
  filename.jpg               ← UI parameter images (no prefix)
```

### manifest.json (Unchanged)

```json
{
  "packageVersion": "1.0",
  "workflowName": "My Workflow",
  "environmentLibraries": ["Kitchen Library"],
  "actionLibraries": ["My Action Library"],
  "createdAt": "2026-04-04T12:00:00.000Z",
  "files": [
    { "path": "My Workflow.WFmaster", "type": "workflow" },
    { "path": "environments/Kitchen Library.WFenvir", "type": "environment" },
    { "path": "actions/My Action Library.WFaction", "type": "action" },
    { "path": "images/123456-photo.jpg", "type": "image" }
  ]
}
```

## 8. Migration Guide for Runtime

### Minimum Changes Required

1. **Parse `children` array** — check for `children` first, fall back to `child_workflows`
2. **Accept `schemaVersion: "4.0"`** — same structure as 3.0 with additions above
3. **Read `parentChildSpecId`** on child entries if you need to reconstruct the tree from a flat list
4. **Ignore `version` and `state`** if the runtime doesn't need lifecycle tracking (they're informational)

### Recommended Changes

1. **Use `version` and `state`** to select which workflow version to execute (e.g., only run `Effective` workflows)
2. **Store `parentChildSpecId`** for proper child workflow tree reconstruction
3. **Stop reading `child_workflows`** once all deployed packages are v7.0+ (future deprecation)

### No Changes Needed

- ZIP structure is identical
- manifest.json format is identical
- Step types, connections, parameters, form layouts — all unchanged
- Environment and action library formats — unchanged
- Image storage and naming — unchanged
